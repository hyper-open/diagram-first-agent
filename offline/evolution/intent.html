阶段 6：意图识别与路由

一个“查订单到哪了”的请求，不应该进入一个可以退款、发邮件、改地址的通用 Agent。

一图看懂

flowchart LR Q["用户请求"] --> G["API Gateway"] G --> R["Intent Router"] R -->|"FAQ"| F["FAQ / 知识库"] R -->|"查询"| W["固定工作流"] R -->|"探索"| A["Agent Runtime"] R -->|"高风险/低置信"| H["人工"] R -->|"不确定"| C["澄清追问"] A --> M["Model Gateway"] A --> T["Tool Gateway"] A --> K["RAG"]

一图看懂 · 在 Agent 之前加一层路由：它不回答，只决定“下一步交给谁”

1粗分

售前 / 售后 / 技术 / 投诉。

2细分

退款 / 换货 / 物流 / 账户。

3置信度

高置信直接路由，中置信澄清，低置信人工。

4兜底

任何 handler 都可以说“这不像我的问题”。

本章另有 2 张图：图 1 置信度分叉，图 2 一次请求的路由时序。

置信度决定路径

见图 1：

flowchart TD I["意图 + 置信度"] --> H{"置信度 >= 0.8 ?"} H -->|"是"| R["路由到 handler"] H -->|"否"| M{"置信度 >= 0.5 ?"} M -->|"是"| C["澄清 / 通用路径"] M -->|"否"| U["人工 / 兜底"]

图 1 · 没有“不确定”出口的路由器，会把边界样本硬塞进错误路径

一次请求的路由时序

见图 2：

sequenceDiagram autonumber participant U as 用户 participant R as Intent Router participant H as Handler U->>R: 请求 + 用户/租户上下文 R->>R: 规则 → 语义/分类 → 置信度 alt 高置信 R->>H: 路由到对应 handler H-->>U: 结果 else 中置信 R-->>U: 澄清问题 / 走通用路径 else 低置信或高风险 R->>H: 转人工，附摘要与建议 end

图 2 · 路由层只做分流；具体处理仍由各自的 handler 完成

路由方法

方法 适合 代价
规则/关键词 明确、高频、强合规 覆盖有限，容易被改写绕过
嵌入/语义 同义表达多 边界样本易混，需要阈值
小分类模型 延迟低、成本低、可批量 需要标注与持续维护
LLM 分类 冷启动快、复杂表达 贵、慢、可能编造
分层路由 意图多、可解释 错误逐层累积

实践常用混合路由：规则兜底 + 嵌入/小模型主路由 + LLM 处理低置信/长尾。

命中的目的地

目的地 适合 特点
直接回答 闲聊、简单事实 最快最便宜
FAQ / 知识库 标准问题 可控、可引用
固定工作流 查单、改地址 稳定、可测试
RAG 文档型问题 有证据、可引用
Agent 需要探索、多步、工具组合 灵活、成本高
人工 高风险、低置信、投诉 安全、可兜底

它解决了什么，又制造了什么

解决了 同时制造了
简单请求不再走大模型 误分类：上游错，下游再强也没用
延迟下降一个数量级 歧义与多意图：一句话包含两件事
固定流程比自由循环更稳 分布漂移：新产品/新政策让旧分类器失效
高风险请求不走万能 Agent 路由本身也有延迟
每条路径可独立监控/评测 错误级联：路由错 → 检索错 → 回答错

够用 进入下一阶段

参考答案与自检

1. 设计 5 条路由并写出低置信兜底 要点：每条路由都要有“上升”和“下降”两个出口——高置信直接走，低置信要么澄清、要么降级到更保守的路径（RAG → Agent → 人工）。 自检：如果五条路由的兜底全是“转人工”，等于没有设计兜底——人工是最后的出口，不是默认出口。

2. 置信度阈值应该由什么决定 要点：由误路由的代价决定，而不是由“准确率好看”决定。漏放一个退款请求（应人工却走了 Agent）与多问一句“您是要查订单还是退款”，成本完全不同。 参考：本章开头的“置信度决定路径”图给了 0.8 / 0.5 两档，你的系统可以不同，但要能说出为什么不同。

3. 线上误分类怎么排查 要点：先看分布（低置信率是否突增、新意图是否涌现），再看规则（阈值是否被改过），最后看样本（把误分类的样本按 handler 分组）。 自检：如果第一反应是“再补几条提示词”，说明还没把路由当成一个有监控指标的服务——见本章「优化与度量」的路由准确率、低置信率、误路由代价三个指标。
