阶段 4：工具网关

Agent 的权限，不应该由模型“自称”，而应该由系统“签发”。

一图看懂

flowchart TB A["Agent Runtime"] --> G["Tool Gateway"] G --> R["工具注册 · 协议适配<br/>MCP / OpenAPI / CLI / 沙箱"] G --> P["策略 · 鉴权 · 配额"] G --> C["凭证托管 · 审计 · 计量"] R --> T["MCP / 内部服务 / 沙箱"]

一图看懂 · 工具网关（Tool Gateway）是 Agent 的“能力总线”：统一协议、鉴权、限流、审计

1注册

工具目录、schema、版本、负责人。

2授权

这个用户/租户/Agent 能不能调用？

3执行

注入短期凭证，路由到 MCP/服务/沙箱。

4留痕

结果规范化、审计、计量、脱敏。

本章另有 3 张图：图 1 一次调用的生命周期，图 2 能力令牌，图 3 关键设计原则。

它和另外两个网关的区别

网关 边界 解决的问题
API Gateway 客户端 → 平台 认证、租户、限流、WAF
Model Gateway Agent → 模型 多模型、路由、回退、计费
Tool Gateway Agent → 工具/执行环境 注册、鉴权、权限、审计、协议适配、沙箱路由

新问题：能力越大，边界越重要

风险 表现 防线
混淆代理 Agent 有权限，用户没有 权限绑定最终用户；每次调用都授权
间接注入 网页/工具结果里藏指令 数据标记、出口控制、高风险审批
工具投毒 第三方 MCP/插件描述藏指令 来源审查、版本锁定、隔离运行
Schema 漂移 工具升级后参数变了 版本化、兼容性检查、灰度
长任务 构建/爬取跑几分钟 异步任务 + 任务 ID + 检查点
结果过大 全量日志/网页撑爆上下文 分页、截断、外置存储 + 引用

网关骨架
python
class ToolGateway:
    def invoke(self, ctx, name, args):
        tool = self.registry.get(name)
        if tool is None:
            return error("unknown_tool", hint=self.registry.names())

        validate(args, tool.schema)
        decision = self.policy.check(ctx.user, tool, args)
        if decision == "deny":
            return error("permission_denied", retryable=False)
        if decision == "approval":
            return approval_required(tool, args)

        credential = self.credentials.issue(ctx.user, tool, ttl=300)
        result = tool.invoke(
            args,
            credential=credential,
            idempotency_key=ctx.request_id,
        )
        self.meter.record(ctx, tool, result)
        return normalize(result)

度量与阶段边界

指标 说明
工具成功率 按工具/租户分桶
权限拒绝率 可能是攻击信号，也可能是配置错
审批通过率 / 等待时间 审批是否成为瓶颈
幂等命中率 / 重复副作用 写操作是否安全
P95 延迟 按工具类型
结果截断率 / 超时率 长任务与结果大小
够用 进入下一阶段
工具同团队、本地、同步 需要私有知识、引用、权限过滤
凭证由宿主直接持有 知识库需要租户/文档级 ACL
无高风险写操作 需要 Agentic RAG / 多跳检索

参考答案与自检

1. 能力令牌的最小字段 要点：subject（真实用户/租户）、action、resource、expires_at、max_uses，以及可选的 approval_id。少任何一个都会退化成“Agent 自己说了算”。 自检：如果令牌里有“Agent 身份”却没有“用户身份”，这就是混淆代理的入口。

2. 设计一次工具调用的完整生命周期 要点要覆盖：鉴权 → 策略判定（允许/拒绝/审批）→ 签发短期凭证 → 注入幂等键执行 → 超时与错误规范化 → 脱敏 → 审计落盘。 自检：审计记录里如果只有“调用了工具 X”而没有 subject / resource / approval_id / 结果状态，事后无法追责。

3. 工具投毒与 Schema 漂移 要点：投毒防线是来源审查 + 版本锁定 + 隔离运行；漂移防线是工具 schema 的版本化与兼容性检查（新增必填字段会打挂老 Agent）。 自检：能说清“MCP 只统一了连接方式，没有统一信任等级”算过关。
