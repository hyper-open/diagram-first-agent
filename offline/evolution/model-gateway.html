阶段 3：模型网关与路由

当系统从“一个模型”变成“多个模型 / 多个供应商”，模型访问就不再是业务代码里的 if/else。

一图看懂

flowchart TB A["Agent / 应用"] --> G["Model Gateway"] G --> R["路由 · 配额 · 重试/回退"] G --> M["缓存 · 计量 · 追踪"] R --> P["Provider A / B / 自托管"] M --> O["账单 · 监控 · 审计"]

一图看懂 · 模型网关（Model Gateway）把“鉴权、路由、配额、回退、计量”收拢到一个内部服务

1鉴权与配额

这个请求属于谁？还有没有预算？

2路由

按任务、租户、成本、延迟选模型。

3调用与回退

失败时换 provider，而不是让业务代码重试。

4计量与观测

记录 usage、成本、延迟，进入账单与 trace。

路由策略 做法 风险
静态 任务类型 → 固定模型 边界变化要改配置
规则 按租户/长度/语言/SLA 规则会越来越多

级联 小模型失败再升级 失败请求延迟叠加
成本/延迟感知 满足质量下选最便宜/最快 需要持续评测质量
灰度/影子 小流量对比新模型 需要双倍调用与对比体系

它解决了什么，又制造了什么

解决了 同时制造了
每家 SDK / 协议不同 多一跳延迟
API Key 散落各服务 网关单点故障
无法统一限流与配额 路由错误：简单任务送贵模型，复杂任务送小模型
供应商挂了自己写回退 计费口径不一致：token、缓存、图片计费不同
不知道谁花了多少钱 缓存正确性：相似不等于相同
换模型要改所有调用点 网关持有全部密钥，成为高价值目标

网关骨架
python
class ModelGateway:
    def chat(self, ctx, messages, tools=None):
        self.quota.check(ctx.tenant, ctx.task_type)
        route = self.router.pick(ctx, messages)
        last_error = None

        for candidate in route.candidates:
            try:
                resp = self._call(candidate, messages, tools)
                self.meter.record(ctx, candidate, normalize_usage(resp.usage))
                return resp
            except RetryableError as exc:
                last_error = exc
                continue
            except NonRetryableError:
                raise

        raise GatewayExhausted(route, last_error)

参考答案与自检

1. 画出你当前系统的网关图 要点：图上要能回答三件事——哪些调用不经过网关（这是最大的风险点）、凭证从哪里来、失败时降级到什么。 自检：如果画完发现所有模型调用都直连、密钥散落在各服务，那么这张图的价值就在于它暴露了问题，而不在乎画得多漂亮。

2. 找一条“模型能直接访问密钥”的路径 要点：常见路径是工具进程从环境变量读密钥、或网关把上游 key 透传给沙箱。修复方向是“凭证不进模型、不进沙箱，由网关按真实主体注入短期 token”（见工具网关）。 自检：修复方案如果写成“在提示词里告诉模型不要泄露”，属于未通过。

3. fallback 应该对哪些错误生效 要点：只对 429 / 5xx / 超时 这类可重试且与内容无关的错误回退；对 400 / 内容审核拒绝 / schema 不符 回退，会把同一个坏请求重复打给多个供应商（既浪费钱又不解决问题）。 自检：能说出“回退是换一个执行者，不是换一个问题”即达标。
