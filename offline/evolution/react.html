阶段 1：ReAct，最小可用 Agent

一次调用只能“答”，ReAct 让模型开始“做”。

一图看懂

flowchart LR U["用户目标"] --> L["Loop"] L --> M["LLM"] M -->|"动作提议"| L L -->|"执行"| T["本地工具"] T -->|"观察"| L L -->|"最终答案"| O["输出"]

一图看懂 · ReAct 只有四个部件：循环、模型、本地工具、输出

1模型决定动作

输出 Thought + Action，而不是直接给答案。

2循环执行动作

由宿主程序解析并调用本地工具。

3观察回到模型

工具结果成为下一轮的 Observation。

4模型决定继续或停止

信息够了就输出 Final Answer，否则继续循环。

本章另有 2 张图：图 1 一次循环的时序，图 2 最常见的失控回路。

一次循环的时序

见图 1：

sequenceDiagram autonumber participant U as 用户 participant L as Agent Loop participant M as LLM participant T as 本地工具 U->>L: 目标 loop 直到 Final Answer / 达到步数上限 L->>M: 目标 + 历史观察 + 工具说明 M-->>L: Thought + Action L->>T: 执行 Action T-->>L: Observation end L-->>U: Final Answer

图 1 · 循环的燃料是 Observation；没有新观察，循环就没有意义

它解决了什么，又制造了什么

解决了 同时制造了
事实幻觉：可以用检索/数据库结果纠偏 文本协议脆弱：格式漂移、JSON 坏掉
计算错误：可以调用计算器/代码 循环失控：原样重试、无预算、无停滞检测
单步规划不够：可以根据中间结果改计划 工具错误不可行动：模型只看到 Error: 500
不能操作外部世界：动作空间扩展到工具 没有状态与追踪：进程一挂任务就没了
过程不可见：Thought/Action 轨迹可读 注入面直接暴露：工具结果里的指令可能被执行

最常见的失败回路

见图 2：

flowchart LR E["工具报错"] --> R["模型原样重试"] R --> L["重复动作 / 上下文膨胀"] L --> S["预算耗尽 / 停滞"] V["外部验证 / 停滞检测"] -.->|"打断"| R B["预算与最大步数"] -.->|"兜底"| S

图 2 · ReAct 的失控通常不是“想错了”，而是“没有新信息还继续”

第一轮工程化：不换架构，先补护栏

可复制模板

本章的清单有对应的结构化版本：mini_agent_config.json。全部模板见 examples/templates/README.md。

护栏 解决的问题
最大步数 防无限循环
token/时间/工具调用预算 防成本与延迟失控
结构化工具错误 让模型知道“能不能重试、怎么改”
外部验证器 防止模型过早宣布完成
trace 出问题能还原每一步
停滞检测 重复调用时及时停止
最小实现（约 20 行）
python
def react_loop(goal, tools, llm, max_steps=8):
    history = []
    for step in range(max_steps):
        prompt = build_prompt(goal, tools, history)
        text = llm.complete(prompt)

        if "Final Answer:" in text:
            return text.split("Final Answer:", 1)[1].strip()

        action, args = parse_action(text)
        observation = tools[action](**args)
        history.append((text, observation))

    return "达到最大步数，任务未完成"

阶段边界

什么时候够用 什么时候进入下一阶段
内部工具、单团队、低风险 工具数量变多、模型经常选错
工具 < 10 个、只读或可逆 工具来自不同团队，需要鉴权/审计
单模型、单租户、无精细计费 要接多家模型、做回退与成本控制
任务分钟级、失败可重来 需要私有知识、引用、权限过滤

下一阶段先解决最痛的一个：动作协议。

参考答案与自检

本章正文的「练习」以 TIP 形式出现在「第一轮工程化」表格之后：

1. 把 max_steps 改成 1，观察 status 和 output 要点：status 应为 partial（预算耗尽不等于失败），output 应包含已完成的部分与失败原因，而不是空字符串或抛异常。 参考实现见 examples/mini_agent/agent.py 的 _partial_output()：它把“已执行步数 / 最近观察 / 建议下一步”写进输出。 自检：如果你拿到的是 error 或异常，说明循环把“资源耗尽”当成了“程序错误”——见优化手册。

2. 改成 3，观察停滞检测何时触发 要点：同一个工具、同一组参数连续出现第 3 次时触发（阈值可配），而不是等到步数耗尽。参数“略有不同但语义相同”（如 1+1 与 1 + 1）能否识别，取决于你是否对参数做了规范化。 自检：能说清“停滞是启发式，max_steps 是硬兜底，两者不能互相替代”即达标。
