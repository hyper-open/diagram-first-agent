前沿与趋势：哪些会留下，哪些只是补丁

一图看懂

flowchart LR C["能力内化"] --> P["协议与身份"] --> E["评测与可靠性"] --> L["长程任务"] --> H["人机协作"]

一图看懂 · 前沿不是一串产品名，而是五条结构性变化：能力、协议、评测、长程、交互

技术演进史告诉我们：很多“技巧”只是当前模型缺陷的补丁。模型升级后，补丁会消失，但系统问题会留下。

这一章不追新闻，而是给一组判断框架，帮你在新概念出现时快速定位：它解决的是能力问题，还是工程问题？

一、正在发生的五个方向

1. 能力内化：模型吃掉外部脚手架

过去需要外部系统做的事，正在被模型内化：

  • 工具调用从“文本解析”变成原生能力。
  • 长上下文减少了一部分检索需求。
  • 推理模型承担了更多规划/检查。
  • 多模态模型直接读截图/文档。

这带来一个判断：

如果一个技术只是在“绕过模型缺陷”，它大概率是过渡方案；如果它在解决“系统约束”，它会长期存在。

例如：

  • 为了让模型输出 JSON 而写的复杂正则 → 过渡。
  • 权限、沙箱、幂等、审计 → 长期。
  • 用多 Agent 模拟“分工”以弥补单模型上下文不足 → 可能过渡。
  • 用多 Agent 做并行探索/独立评审 → 长期。

2. 长程任务：从分钟到小时

Coding Agent、Deep Research 把任务时长推到小时级。长程任务暴露的新问题：

  • 状态管理：进程重启、上下文丢失、任务恢复。
  • 检查点：哪些步骤可重放，哪些副作用不可逆。
  • 预算：成本随时间线性增长，需要动态控制。
  • 人机协作：什么时候该问、该停、该交给人。
  • 评测：长轨迹的成功归因困难。

未来的 Agent 工程会更像分布式任务系统 + 人机协作界面，而不是“一个更长的 prompt”。

3. 协议与生态：MCP、A2A、Agent 身份

  • MCP 统一工具/资源接入，降低集成成本。
  • A2A 尝试标准化 Agent 间委派与协作。
  • Agent 身份/支付/授权 仍在早期：Agent 代表谁、能花多少钱、能签什么合同？

协议解决“怎么连”，但不解决“能不能信”。身份、权限、责任归属会是长期议题。

4. 评测与可靠性：从 demo 到可运营

行业正在从“演示效果”转向：

  • 可复现的评测集与轨迹评测。
  • 线上监控、影子流量、金丝雀。
  • 成本/延迟/成功率的联合优化。
  • 安全红队与合规审计。

一个信号：越来越多团队把“Agent 评测”当成独立基础设施，而不是附属于模型评测。

5. 交互形态：从聊天框到“同事”

  • 后台任务/定时触发，而不是一问一答。
  • 多模态输入输出（屏幕、语音、文档）。
  • 人机协作：审批、接管、纠错、教学。
  • Agent 作为“软件的用户”：API/界面需要为 Agent 设计（agent-readable）。

这会改变产品设计：不再只是“输入框 + 回答”，而是任务面板、进度、证据、审批、回滚。

二、仍然没有答案的五个问题

1. 提示注入能彻底解决吗？

目前没有通用解法。模型难以可靠区分“数据”和“指令”，而 Agent 又必须接触不可信内容。

短期靠系统隔离 + 权限 + 人工确认，长期可能需要模型层面的指令层级/能力控制。不要把“加一句不要执行”当解决方案。

2. 如何可靠地验证开放任务？

代码有测试，数学有答案，但研究、写作、策略建议没有唯一正确答案。

可能的路径：

  • 把开放任务拆成可验证的子断言。
  • 用多源证据/引用核对。
  • 人类反馈 + rubric。
  • 过程可信（工具使用、来源）替代结果唯一正确。

3. 记忆能“学会”而不只是“存储”吗？

现在的记忆大多是检索式：存进去、取出来。真正的学习需要：

  • 从经验中提炼可复用策略。
  • 知道何时该更新/放弃旧策略。
  • 避免错误经验被固化。

程序性记忆（技能库）是一个有希望的方向，但如何验证、版本化、迁移仍是问题。

4. 多 Agent 的收益能稳定超过成本吗？

多 Agent 在并行、隔离、独立评审上有价值，但通信损耗、错误传播、责任不清是硬问题。

未来可能不是“很多通用 Agent 聊天”，而是少量专用 Agent + 确定性编排 + 清晰契约。

5. 责任与合规如何落地？

当 Agent 造成损失，谁负责？开发者、部署者、模型提供方、用户？

可审计的轨迹、权限边界、人工审批、保险与合同，可能比模型能力更决定 Agent 能否进入关键行业。

三、一张“炒作 vs 现实”对照表

说法 现实
“Agent 会自己完成一切” 开放任务仍需人设定边界、验证、兜底
“多 Agent 一定更强” 只在并行/隔离/独立评审时可能更强
“长上下文取代 RAG” 长上下文装得下，检索/压缩决定装得对
“记忆就是向量库” 写入、冲突、遗忘、隔离才是难点
“Computer Use 什么都能做” 慢、脆、难验证，优先 API/DOM
“提示词工程过时了” 基础指令设计仍重要，只是不再是全部
“模型越强，工程越不重要” 能力越强，权限/验证/可观测越重要

四、值得跟踪的信号

不要追每个新模型，跟踪这些结构性变化：

  1. 模型原生支持的工具/协议：是否减少了外部胶水？
  2. 上下文与记忆机制：是否从“检索”走向“可学习的状态”？
  3. 评测标准：是否从“单轮答案”走向“长程轨迹 + 成本 + 安全”？
  4. 身份与授权：Agent 是否能安全地代表用户行动？
  5. 运行时隔离：沙箱是否成为默认基础设施？
  6. 交互范式：是否从聊天转向任务/审批/协作？
  7. 成本曲线：推理成本下降后，哪些架构会变得可行？

五、给学习者的建议

可复制模板

本章的清单有对应的结构化版本：preflight_checklist.json。全部模板见 examples/templates/README.md。

1. 先把“不变的部分”学扎实

  • 循环、状态、预算、终止。
  • 上下文组装与压缩。
  • 工具设计、错误契约、权限。
  • 评测、追踪、失败分类。
  • 沙箱与最小权限。

这些不会因为模型升级而失效。

2. 对新框架保持“可替换”心态

框架值得学，但要知道它替你做了什么。建议至少手写一次：

  • 一个 Agent 循环。
  • 一个工具注册/校验层。
  • 一个带 trace 的评测 harness。
  • 一个最小沙箱执行器。

3. 用项目驱动

选一个你真正需要的任务，做完整闭环：

text
定义成功 → 建评测 → 做原型 → 找失败 → 按层优化 → 上线监控

这比读十个框架文档更能建立判断力。

4. 保持安全直觉

每加一个工具、一个权限、一个外部内容源，都问：

  • 最坏情况是什么？
  • 能不能回滚？
  • 谁有权批准？
  • 出了事能不能查到？

六、结语：Agent 是系统问题

Agent 的迷人之处在于“自主”，但它的工程本质是在不确定性中建立可控性：

  • 用循环获得适应力。
  • 用上下文获得相关性。
  • 用工具获得行动力。
  • 用记忆获得连续性。
  • 用编排获得可控性。
  • 用沙箱获得安全性。
  • 用评测获得可改进性。

模型会继续变强，但这些层不会消失。把每一层的契约设计好，你就能在模型换代时保留大部分系统价值。

参考答案与自检

本章没有「练习」，用三条自检替代：

1. 能否把新概念归到“能力问题”还是“工程问题”？ 要点：按本章的判断框架——只在绕过模型缺陷的技术会消失，解决系统约束的会留下。任取一个当下的热点（如“长上下文取代 RAG”“新 Agent 框架”），能在一分钟内归类并给出理由。 自检：如果归类理由是“大厂都在推”，说明还没建立判断框架。

2. 能否说出一个“只是补丁”的技术？ 要点：例如“用正则兜底解析 JSON 输出”“用提示词逼迫模型不要泄露系统提示”——它们的共同点是依赖模型的特定缺陷，模型升级后即失效。 自检：如果举不出反例（只能举会留下来的技术），判断力还不够。

3. 五条结构性变化能否复述 要点：能力内化、协议与身份、评测与可靠性、长程任务、人机协作——并能各举一个当前证据（论文、规范或产品行为）。 自检：如果只能复述名字，说不出证据，说明这一章读成了列表。
